Upgrade Path / Migration Checklist

Every deprecation, removal, and breaking change tracked across the version history, plus the operational notes that matter most when planning an upgrade.

🔧 Planned changes (roadmap, not yet shipped)

Breaking changes announced in the Roadmap (Red Hat Product Management's quarterly What's New & What's Next deck) ahead of the release that ships them. Subject to change; plan for them, don't act on them yet.

3.6 (Q4 2026): FMS-Guardrails Orchestrator (via TrustyAI) ⚠️ planned

What will change: Removal of FMS Guardrails targeted for Q4 2026 (RHAI 3.6). NeMo Guardrails is the default guardrail service going forward.
Migration action: Migrate workloads off FMS Guardrails Orchestrator to NeMo Guardrails before upgrading to 3.6. The deck targets removal in Q4 2026 on top of the 3.5 deprecation.

3.6 (Q4 2026): Evaluation Stack -> EvalHub ⚠️ planned

What will change: Deprecate LMEvalJob in favor of a native LM-Eval-Harness EvalHub adapter.
Migration action: Stop authoring new LMEvalJob custom resources. Port existing evaluation jobs to the EvalHub SDK/CLI with the native LM-Eval-Harness adapter before upgrading to 3.6; LMEvalJob is targeted for deprecation in the same release (Q4 2026).

3.6 (Q4 2026): AI Gateway - Praxis data plane (replacing the Envoy-based MaaS gateway) ⚠️ planned

What will change: The Praxis-based AI Gateway becomes the data plane for the MaaS control plane (Subscriptions, API Keys, AITenant, Gen AI Studio stay), replacing the fragmented Envoy + IPP + shim stacks with one governed hop: same RBAC and quotas (Kuadrant/RHCL), body-based routing, provider API translation, credential injection, GenAI observability, and a path to GA without maintaining two gateway implementations.
Migration action: Plan MaaS gateway migration off the Envoy-based data plane: Envoy + IPP provider-translation filters and Istio/Kuadrant auth-rate policies move onto the Praxis data plane over time. The deck commits to same RBAC/quota behavior (Kuadrant/RHCL) but HttpRoute/provider-translation configuration will change - keep gateway config under version control and test against Praxis in EA before the cutover.

3.6 (3.6 GA): Notebooks 2.0 (WorkspaceKind-based next-gen workbench model) ⚠️ planned

What will change: Notebooks 2.0 Tech Preview: trial the new WorkspaceKind-based model while a migration path from Notebooks 1.x is defined.
Migration action: Do not build new automation against Notebooks 1.x assumptions (per-workbench custom resources). A Notebooks 1.x -> 2.0 migration path is being defined alongside the 3.6 TP - keep workbench provisioning scripted and re-validate it against WorkspaceKinds before committing to 2.0.

3.6 (Q4 2026): AI Safety Operator (TrustyAI Operator rename) ⚠️ planned

What will change: Renaming TrustyAI Operator to AI Safety Operator, plus refactoring the TrustyAI Service from Java to Python (both targeted Q4 2026).
Migration action: Breaking rename: update automation, Argo CD apps, and operator subscriptions that reference the TrustyAI Operator name/GVK before the Q4 2026 release. The backing service is also refactored from Java to Python - re-validate TrustyAI-service API consumers and custom images against the refactored runtime.

Upgrade-path operational notes

Upgrade Path

3.0 and 3.2 offered no upgrade path from 2.x at all -- new installs only. 3.3.2 specifically (not 3.3.0/3.3.1) is the first 3.x release supporting migration from 2.x, and only from 2.25.4 or later -- a precise version gate. This is a migration with significant component changes, not zero-downtime: requires a proactive support case, complete backup, prerequisite checks, and the rhai-cli migration assessment process. Unconverted ModelMesh/KServe Serverless models return HTTP 503 immediately after upgrade with no grace period; OGX (Llama Stack) data is permanently lost during migration unless backed up beforehand, with no automated migration path. Custom workbench images built against oauth-proxy must be rebuilt for kube-rbac-proxy or they fail with redirect loops. RHOAI 3.3 requires OpenShift 4.19.9 specifically. Release cadence: EA1 (1 month, unsupported) -> EA2 -> GA (7 months full support); EUS releases add 11 more months on top; one EUS release per three GA releases.

Upgrade Path

At 3.5 GA, a dedicated migration guide ('Assess and plan for migration from 2.25.9+ to 3.5') ships using rhai-cli, covering side-by-side and in-place approaches, Kueue management-state prerequisites, and component-specific rhai-cli migrate actions for Kueue/RHBOK, AI Pipelines, Model Serving, Workbenches, TrustyAI, Training, Llama Stack/OGX, and Ray. After upgrading, move off the support-required-upgrade-3.5 channel onto stable-3.5 / stable-3.x / eus-3.5 per lifecycle needs. New 3.5-specific item: anyone who configured llm-d flow control during the 3.4 TP window must update the API group, metrics prefix, and saturation-detector configuration path before/during the 3.5 upgrade.
