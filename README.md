# RHOAI Version Tracker

A self-updating, color-coded static site tracking Red Hat OpenShift AI's
version history, feature lifecycle, deprecations, and upgrade paths —
cross-checked against the live [Supported Configurations for 3.x](https://access.redhat.com/articles/rhoai-supported-configs-3.x)
matrix so the release notes' claims and the formal support matrix's claims
are never silently collapsed into one answer when they disagree.

**Live site:** enable GitHub Pages (Settings → Pages → Deploy from branch →
`main` / `/docs`) and it will be served from this repo's `docs/` folder.
Rebuilding and pushing is the entire deploy step — no workflow required.

## How it works

No LLM API key is used anywhere in this pipeline. Deterministic steps run as
plain Python; the judgment-heavy synthesis steps (entity resolution, breaking-
change detection, conflict flagging, risk coloring, narrative writing) are
performed by an agent session on demand, following the checklist in
[`prompts/synthesize_release.md`](prompts/synthesize_release.md) for shipped
releases and [`prompts/synthesize_roadmap.md`](prompts/synthesize_roadmap.md)
for roadmap decks.

```
data/raw/<version>.pdf            official release notes (not committed — see below)
      │
      ▼
scripts/extract_release_notes.py  deterministic PDF → JSON (font-heuristic, chapter-tagged)
      │
      ▼
data/extracted/<version>.json
      │                                  scripts/fetch_support_matrix.py
      │                                          │
      │                                          ▼
      │                          data/matrix_snapshots/<date>.json
      │                                          │
      └──────────────┬───────────────────────────┘
                      ▼
     Agent session, guided by prompts/synthesize_release.md:
     entity resolution, status-transition + breaking-change detection,
     conflict flagging, risk coloring, narrative writing
                      │
                      ▼
     data/registry/feature_registry.json  (updated)
     data/diffs/<prev>_to_<new>.json      (new)
                      │
                      ▼
     scripts/validate_registry.py   (schema + sanity checks, no LLM)
                      │
                      ▼
     scripts/build_site.py          (Jinja2 → docs/, no LLM)
                      │
                      ▼
     git commit + push → GitHub Pages serves docs/

      data/raw/<version>-roadmap-deck-<quarter>.pdf   quarterly roadmap deck (not committed)
      │
      ▼
      Agent session, guided by prompts/synthesize_roadmap.md:
      FeatureEntry.planned[] targets (never timeline[]), Planned-status
      features, ga_date_is_target VersionMeta, roadmap_meta provenance
      │
      ▼
      same validate → build → push steps
```

## Repo layout

- `scripts/common/schema.py` — the Pydantic contract every JSON file in this repo must satisfy.
- `scripts/extract_release_notes.py` — PDF → `data/extracted/<version>.json`.
- `scripts/fetch_support_matrix.py` — live matrix page → `data/matrix_snapshots/<date>.json`.
- `scripts/validate_registry.py` — schema/sanity gate, run before every publish.
- `scripts/build_site.py` — renders `templates/*.html` + `data/registry/feature_registry.json` → `docs/`.
- `data/registry/feature_registry.json` — the cumulative rollup (source of truth for the site).
- `data/deprecation_timeline`, `integration_notes`, `operational_notes`, `ogx_provider_table`, `source_conflicts`, `roadmap_meta` all live inside the same registry file.
- `prompts/synthesize_release.md` — the instruction checklist for ingesting a new release.
- `prompts/synthesize_roadmap.md` — the instruction checklist for ingesting a quarterly roadmap deck.
- `templates/`, `assets/` — Jinja2 templates and shared CSS/JS for the site.
- `docs/` — the built, deployable static site. Regenerated by `build_site.py`; don't hand-edit.

## Shipped history vs. roadmap targets

The registry keeps two strictly separate layers:

- **`timeline[]`** — shipped status history, sourced from official release
  notes and the Supported Configurations matrix, append-only. `current_status`
  always reflects the latest *shipped* release.
- **`planned[]`** — forward-looking roadmap targets from the quarterly
  "What's New & What's Next" deck (`RoadmapTarget` rows: version, target
  status, deck window, breaking flag + migration note). A feature whose only
  entries are planned ones has `current_status: "Planned"` and an empty
  timeline; a targeted version (e.g. 3.6, GA targeted November 2026) carries
  `ga_date_is_target` and never counts as the "latest tracked release".

On the site this split is visual: dashed badges/columns mean *planned
roadmap target, not shipped* (Feature Matrix, Roadmap page), and the
Migration Checklist lists planned changes separately from shipped ones.

## Ingesting a new release

1. Drop the new release-notes PDF at `data/raw/<version>.pdf`.
2. Open an agent session in this repo and say **"ingest `<version>`"**.
3. The agent follows [`prompts/synthesize_release.md`](prompts/synthesize_release.md) end to end: run the extractors, update the registry, validate, build the site, and review before pushing.

## Ingesting a roadmap deck

1. Drop the quarterly "What's New & What's Next" deck at
   `data/raw/<version>-roadmap-deck-<quarter>.pdf` (git-ignored, like all raw PDFs).
2. Open an agent session and say **"ingest roadmap `<quarter>`"**.
3. The agent follows [`prompts/synthesize_roadmap.md`](prompts/synthesize_roadmap.md):
   entity-resolve every "What's Next" item into `planned[]` targets (never
   `timeline[]`), cross-check the deck's "What's New" claims against tracked
   sources, record conflicts, add the targeted `VersionMeta`, validate, build,
   and review before pushing. When the release actually ships, ingest its
   release notes as above — the confirming rows join `timeline[]` and the
   targets stay in `planned[]` as the forecast-vs-actual record.

## Local setup

Same steps as Makefile targets (the venv is created on first use):

```
make setup          # create .venv and install requirements.txt
make extract        # PDF -> data/extracted/3.5.json (make extract VERSION=3.6 to change)
make fetch-matrix   # live Supported Configurations matrix -> data/matrix_snapshots/
make validate       # schema + sanity gate on the registry
make build          # render the static site into docs/
make serve          # preview docs/ at http://localhost:8765
make all            # extract -> fetch-matrix -> validate -> build
```

Or by hand:

```
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt

python scripts/extract_release_notes.py data/raw/3.5.pdf
python scripts/fetch_support_matrix.py
python scripts/validate_registry.py
python scripts/build_site.py
python -m http.server 8765 --directory docs   # preview locally
```

## Why release-notes PDFs aren't committed

This repo is public. Red Hat's release-notes PDFs are copyrighted documents,
so `data/raw/*.pdf` is git-ignored (see `.gitignore`) — download your own
copy from [docs.redhat.com](https://docs.redhat.com) to re-run the extractor
locally. The **derived, factual data** extracted from them
(`data/extracted/*.json`, the registry, the rendered site) is committed and
published, the same way the reference research document this project started
from cites and summarizes those PDFs without redistributing them.

## Source precedence

When sources disagree and a single answer is needed for formal support
status: **Supported Configurations matrix → release notes → product guides →
press coverage (corroboration only)**. Roadmap decks sit at the same level as
press coverage — corroboration and forward-looking targets only, never origin
for a shipped status claim. Every open disagreement is listed, not silently
resolved, on the site's [Source Conflicts](docs/conflicts.html) page.
